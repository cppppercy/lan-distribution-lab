# 技术决策记录（ADR 摘要）

> 此处记录“为什么”，不等于相关代码已经实现。状态只用 PROPOSED / ACCEPTED / SUPERSEDED。

## ADR-001（ACCEPTED，2026-11-08）：中心服务器优先
- **背景**：个人开发，Windows 主机、手机和平板，需要兼顾使用价值与可靠性实验。
- **决定**：首版采用中心文件服务器 + 移动浏览器 + Python 专用测试客户端。
- **理由**：保证基础功能可交付，并支持可控的断点续传与并发对照。
- **代价**：中心服务器可能是带宽瓶颈；不等于真正 P2P。
- **撤销条件**：通过网络实验发现中心模型无法满足核心场景，另开 ADR 决定。

## ADR-002（ACCEPTED，2026-11-08）：HTTP/TCP 为基础传输
- **决定**：基础文件收发使用 HTTP over TCP；恢复下载采用 RFC 9110 的 Range/资源版本校验；UDP 桌面发现延后为 P1。
- **理由**：成熟互操作性、浏览器可访问、可抓包、可实施确定性恢复测试。
- **限制**：不能声称移动浏览器全面支持应用控制的断点续传，也不需要重写 TCP 的可靠字节流。
- **参考**：https://www.rfc-editor.org/rfc/rfc9110.html

## ADR-003（ACCEPTED，2026-11-08）：真实网络与模拟负载分离
- **决定**：手机、平板在真实 Wi-Fi 上测试基本/双客户端分发；电脑多进程用于更高并发与故障测试。
- **理由**：避免把同机测试误认为真实无线网络性能。
- **验证**：实验记录必须注明设备、链路、文件、迭代次数和指标。

## ADR-004（ACCEPTED，2026-11-08）：小步 AI 接力开发
- **决定**：GitHub 是共享状态；Codex 主实现，DSH 备用；每任务有可验证验收与交接记录。
- **理由**：减少长任务失控和工具切换导致的信息损失。
- **限制**：付费服务、范围变化、合并 PR、危险文件操作须经用户批准。

## ADR-005（PROPOSED）：上传接口与移动端认证细节
- **待定**：短时访问令牌/配对流程、上传配额、文件冲突策略、SQLite Schema、具体端点。
- **要求**：在 T002 完成威胁模型和 API 契约后决定，不允许 T001 先行硬编码。
