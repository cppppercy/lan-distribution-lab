# 技术决策记录（ADR 摘要）

> 此处记录“为什么”，不等于相关代码已经实现。状态只用 PROPOSED / ACCEPTED / SUPERSEDED。

## ADR-001（ACCEPTED，2026-11-08）：中心服务器优先
- **背景**：个人开发，Windows 主机、手机和平板，需要兼顾使用价值与可靠性实验。
- **决定**：首版采用中心文件服务器 + 移动浏览器 + Python 专用测试客户端。
- **理由**：保证基础功能可交付，并支持可控的断点续传与并发对照。
- **代价**：中心服务器可能是带宽瓶颈；不等于真正 P2P。
- **撤销条件**：通过网络实验发现中心模型无法满足核心场景，另开 ADR 决定。

## ADR-002（ACCEPTED，2026-11-08）：HTTP/TCP 为基础传输
- **决定**：基础文件收发使用 HTTP over TCP；恢复下载采用 RFC 9110 的 Range/资源版本校验；UDP 桌面发现延后为 P1。
- **理由**：成熟互操作性、浏览器可访问、可抓包、可实施确定性恢复测试。
- **限制**：不能声称移动浏览器全面支持应用控制的断点续传，也不需要重写 TCP 的可靠字节流。
- **参考**：https://www.rfc-editor.org/rfc/rfc9110.html

## ADR-003（ACCEPTED，2026-11-08）：真实网络与模拟负载分离
- **决定**：手机、平板在真实 Wi-Fi 上测试基本/双客户端分发；电脑多进程用于更高并发与故障测试。
- **理由**：避免把同机测试误认为真实无线网络性能。
- **验证**：实验记录必须注明设备、链路、文件、迭代次数和指标。

## ADR-004（ACCEPTED，2026-11-08）：小步 AI 接力开发
- **决定**：GitHub 是共享状态；Codex 主实现，DSH 备用；每任务有可验证验收与交接记录。
- **理由**：减少长任务失控和工具切换导致的信息损失。
- **限制**：付费服务、范围变化、合并 PR、危险文件操作须经用户批准。

## ADR-005（SUPERSEDED，2026-11-08）：上传接口与移动端认证细节
- **原待定项**：短时访问令牌/配对流程、上传配额、文件冲突策略、SQLite Schema、具体端点。
- **替代原因**：T002 已将 API、授权和存储边界收敛为可实施契约；具体 SQLite 实现与本地操作者控制面仍留待 T003 选择。
- **后继**：见 ADR-006、ADR-007 与 `docs/API_CONTRACT.md`。

## ADR-006（ACCEPTED，2026-11-08）：短时配对码换取限时会话
- **背景**：手机/平板需要低摩擦连接，CLI 需要可脚本化凭据；同一 Wi-Fi 其他设备默认不可信，首版不建设账号系统。
- **决定**：操作者仅在本机生成 6 位、10 分钟、一次性的配对码，并赋予 `read` 或 `read_write` scope。浏览器成功配对后使用 `HttpOnly; SameSite=Strict` Cookie；CLI 一次取得 256-bit Bearer token，后续仅放 `Authorization` 头。会话绝对过期为 8 小时，可撤销，服务端只存 token 摘要。
- **理由**：无需注册、云身份或付费服务；能区分读写、限制凭据暴露窗口，并适配同源移动浏览器与 CLI。
- **替代方案**：拒绝无认证 LAN、URL token 和长期用户名密码；mTLS/客户端证书保留给未来 HTTPS 调研。
- **限制**：HTTP 不能保护配对码、Cookie 或 Bearer token 免受 LAN 窃听/中间人；QR 只能带服务地址，不能带秘密。Cookie 认证的状态变更须校验 Origin 且默认不开放跨域 CORS。

## ADR-007（ACCEPTED，2026-11-08）：不可变文件快照与服务端对象名
- **背景**：客户端路径和文件名不可信，正在变化的原文件会使 Range/续传把不同版本错误拼接。
- **决定**：每个已发布对象获得服务器生成的 UUID `file_id` 和内部 `storage_key`；对象在受控 `managed_root/objects` 中以不可变快照保存。上传先写入私有 `staging`，流式计算 SHA-256、检查上限后同卷原子发布。展示名仅为元数据，不决定路径；替换内容创建新 `file_id`。
- **理由**：消除路径拼接和同名覆盖，形成稳定的强 ETag（`"sha256:<hex>"`）与文件版本，从而使 T005 的 `If-Range` 和 T006 CLI 检查有明确基础。
- **代价**：导入已有文件会复制占用额外空间，需要配额、最小剩余空间、临时文件清理和普通文件/链接检查。
- **限制**：T002 不建表、不实现 SQLite 或文件导入；T003 必须决定元数据持久化与 Windows reparse-point 的具体安全实现，并用测试验证。

## ADR-008（ACCEPTED，2026-11-09）：SQLite 本机状态库与 CLI 配对控制面
- **背景**：T003-A 需要让“本机生成配对码”与正在运行的服务读取同一状态，同时保证多请求不能重复兑换一个六码，也不把管理能力暴露为 LAN HTTP 接口。
- **决定**：使用 Python 标准库 `sqlite3` 保存配对码、会话、限速状态和未来文件元数据基础；使用独立的 32 字节本机服务器秘密对配对码和 Bearer token 的秘密部分做 HMAC-SHA-256 摘要。通过 `python -m lan_distribution_lab pair create` 本机生成配对码；`pair create` 与 `serve` 使用同一明确的绝对 `data_dir`、独立的绝对 `managed_root`。SQLite `BEGIN IMMEDIATE` 串行化兑换与一次性消费。
- **理由**：标准库无新增服务或付费依赖；数据库和秘密可跨服务重启保留；事务能为同一配对码提供可测量的并发正确性。命令行控制面仅由主机操作员调用，避免新增 LAN 管理端点。
- **替代方案**：拒绝内存字典（重启即失效且跨进程不一致）、明文 token 表（数据库泄露即等同会话泄露）、HTTP 管理端点（扩大攻击面）和第三方认证/云服务（超出课程首版复杂度）。
- **代价与限制**：本机数据目录必须由操作者妥善保护；T003-A 仅尽力设置 POSIX 权限位，未在真实 Windows ACL 上做验证。HTTP 仍不保密；SQLite 不是文件内容存储，也没有在本任务实现配额、清理或 reparse-point 防护。

## ADR-009（ACCEPTED，2026-11-09）：受控流式 multipart 与不可变对象发布
- **背景**：框架表单解析可能在业务逻辑检查前缓存整个 multipart 请求，不能满足上传大小在接收阶段生效的要求；客户端文件名、路径、符号链接及磁盘错误均不可被信任。
- **决定**：T003-B 使用小型单文件 multipart 状态机直接消费 ASGI `Request.stream()`，在接收过程中限制总请求字节、part header 和字段大小；文件内容按 64 KiB 写入私有 staging 并计算 SHA-256。完成后检查 SQLite 总配额、可用磁盘和普通文件边界，以服务器 UUID 的硬链接方式发布到 `objects/`，再写入元数据和任务摘要。
- **理由**：不新增 multipart/数据库依赖，大小拒绝发生在应用接收流期间而非完整表单缓存之后；UUID 对象名与 staging→发布过程避免客户端路径和同名覆盖；硬链接在同一受控卷不覆盖已有对象。
- **替代方案**：拒绝 `await request.form()`/`UploadFile` 作为本任务的大小安全边界；拒绝整文件内存读取、客户端路径落盘和可覆盖的 `os.replace` 发布。保留更成熟 multipart 库作为未来独立评估项。
- **限制**：当前只支持一个文件与可选展示名，不实现上传幂等键、Range 或续传。Windows 受限测试环境不能创建符号链接，虽有 lstat/reparse-point 拒绝代码，仍需在可创建链接的 Windows 环境复核竞态。HTTP 不提供机密性。

## ADR-010（ACCEPTED，2026-11-09）：无秘密状态文件的 CLI 单对象续传
- **背景**：T005 已能为不可变对象提供强 ETag、单 Range 和 If-Range；CLI 需要在进程中断后恢复，但不能把 Bearer token、用户命令或不可信本地字节直接当成可追加状态。
- **决定**：T006 用 Python 标准库 `urllib`，不新增运行时依赖。下载前读取受保护元数据；在目标同目录维护固定的 `.part` 和 `.part.json`。JSON 仅含规范化 server、file_id、强 ETag、大小、SHA-256 与已落盘字节，逐块在数据 `fsync` 后原子更新，绝不含 token 或任意路径。恢复请求为 `Range: bytes=<offset>-` + `If-Range: <ETag>`；只接受精确的 206/Content-Range/Content-Length/ETag。完成后重新流式 SHA-256，并以不覆盖已有目标的同目录硬链接发布。
- **凭据决定**：CLI 不提供 `--token` 参数；默认 `getpass` 无回显输入。`--pair` 以无回显的一次性配对码换取 token，仅保留在本进程内存；`--token-stdin` 仅为调用方已能安全管理的管道保留。
- **失败策略**：续传得到完整 200、416 或元数据/本地状态版本不一致时，将旧工件重命名为随机 `.stale-*` 后至多重新开始一次；错误 206 或最终 hash 失败不追加/不发布。连接错误采用默认两次、可配置但有限的重试；磁盘失败保留可诊断工件且不发布目标。
- **替代方案**：拒绝保存 token 的明文配置文件、URL/query token、全文件内存缓存、直接覆盖目标和无限重试。Windows Credential Manager/加密 token 持久化未引入，避免平台 API 与额外依赖；用户需在新的 CLI 进程中重新安全输入 token 或使用新的配对码。
- **限制**：HTTP 无 TLS 仍不能保护 CLI token 或内容免受同网段窃听；硬链接发布依赖同一目标目录所在文件系统支持硬链接（常见 Windows NTFS 支持）。真实 Windows ACL、断电一致性和真实无线断线仍未实测。

## ADR-011（ACCEPTED，2026-11-10）：T006 审核补修的凭据、完整 `.part` 与统计语义
- **背景**：T006 审核发现三个问题：(1) `urllib` 默认重定向处理会把 `Authorization` 头重放到 `Location` 指向的任意主机、端口或协议；(2) 数据已全部写入但最终校验/发布前退出时，重跑会发送 `Range: bytes=<总大小>-`，服务端返回 416 后丢弃已下载内容；(3) 旧版本 `.part` 被隔离并从零重启后，`DownloadResult.resumed_bytes` 仍记录废弃数据，影响网络实验统计。
- **决定**：
  1. 客户端默认 `opener` 改用自定义 `HTTPRedirectHandler`，服务端返回任何 3xx（301/302/303/305/307/308 等）都不跟随，统一抛出不含 URL、Location 与凭据的 `ProtocolError`；该策略同时覆盖元数据、内容下载和一次性配对码兑换。可注入 `opener` 的测试接缝保留，但生产默认不会向任何其他地址转发 `Authorization`、配对码或请求体。
  2. 发送内容 GET 前先读取本地续传状态：当 `downloaded_bytes == size_bytes` 且 `.part` 实际大小一致时，直接流式 SHA-256 校验并以硬链接发布，不再发起内容下载请求；哈希不符则隔离 `.part`/`.part.json` 且不发布。零字节文件同样适用，全新空文件仍执行一次 200 下载。
  3. `resumed_bytes` 只统计本次成功下载实际复用的旧数据字节；200/416/版本变化触发隔离重启时归零，真实 `Range` 续传时保留复用字节数。
- **理由**：安全问题必须在客户端闭环，不能依赖对端遵守同源约束；完整 `.part` 的本地复用避免重复消耗带宽，才保留断点续传的真实收益；统计语义直接影响后续网络实验结论，必须在重启点显式重置。
- **替代方案**：拒绝引入 requests/httpx 修复重定向（新增依赖并改变现有可注入 opener 设计）；拒绝在完整 `.part` 校验失败时直接删除数据（保留 `.stale-*` 现场供诊断）；拒绝用累计计数器表达 resumed（会把无效旧数据计入）。
- **限制**：仍为 HTTP 明文，同网段窃听无法由客户端修复；Windows ACL、断电一致性和真实无线中断仍未实测；本补修不改变 T005 的 Range 契约和后端 API。
